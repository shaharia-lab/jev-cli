## 1. Summary

`jev` is an unofficial, open-source command-line tool, written in Rust, for TypeSafe AI's **Jev** model.
Jev is a "System One" model: it never generates text. You send a `state` and a map of typed questions
(`noul`, `choice`, `score`) and get back calibrated probabilities over answers you defined. That shape —
a fast, cheap, typed semantic judgment — is a natural fit for the shell: an `if` statement that understands
language.

`jev` makes that judgment available to four audiences from one binary:

1. **Developers** exploring Jev and tuning questions at a terminal.
2. **Shell scripts and CI** using Jev as a semantic condition, via exit codes and JSON.
3. **AI coding agents** calling `jev` as a tool, or connecting to it as an **MCP server**.
4. **Bulk data / ML workflows** running a question set over thousands of rows.

It follows the conventions of `gcloud`, `aws` and `gh`: noun-verb command groups, profiles, layered
configuration, machine-readable output, stable exit codes, shell completions, and signed self-updating
releases.

## 2. Problem

Today the only ways to call Jev are the Playground, raw `curl`, or the Python/JS SDKs. That leaves gaps:

- **No shell-native path.** Using Jev in a script means hand-writing JSON, `curl`, and `jq`, and
  re-implementing retries and error handling each time.
- **The server does not validate reliably.** Live testing found a 1-level Score returns HTTP 200 and an
  11-level Score returns a server error (`05-live-test-findings.md`). Mistakes cost money or produce
  meaningless answers instead of clear errors.
- **Operational rules live in prose.** Retry 408/429/5xx/529 with backoff, honour `retry-after`, stay
  under ~8 concurrent workers, log the resolved model id and `x-typesafe-request-id`, pin versioned
  models — each user has to discover and re-implement these.
- **Easy to leak the key.** `curl -v`, `set -x` and debug logging all expose the bearer token or
  customer data in `state`.
- **No Rust client and no agent-ready tool.** Agents have TypeSafe's skill for *designing* questions but
  no local tool to *execute, validate and batch* them.

## 3. Goals and non-goals

### Goals

- **G1** One-command evaluation from a request file, flags, or stdin, with human and machine output.
- **G2** Make Jev usable as a shell condition: thresholds map to exit codes without parsing JSON.
- **G3** Catch invalid requests locally, before any network call or spend.
- **G4** Reliable bulk runs: bounded concurrency, retries, resumability, cost totals.
- **G5** First-class for AI agents: intent-oriented help, machine-readable command spec, JSON Schemas,
  structured errors, never prompting non-interactively, and an MCP server mode.
- **G6** Secure by default: key in the OS keychain, never in argv or logs; signed, verified updates.
- **G7** Always current: automatic, verified, non-disruptive self-update with a simple opt-out.
- **G8** Maintainable: a clean `jev-client` library crate separated from the CLI, high test coverage,
  fully automated releases.

### Non-goals (v1)

- Generating text, chaining LLM calls, or orchestrating pipelines beyond one question set per call.
- A question-design assistant or prompt optimiser (TypeSafe's agent skill covers question design).
- A local answer cache (answers are not bit-deterministic; caching stores customer state on disk).
- Threshold tuning, evaluation datasets, or accuracy reporting.
- MCP over HTTP; remote/shared server deployments.
- Non-text inputs (the API is text only).
- Telemetry or analytics of any kind.

## 4. Users and key scenarios

| Persona | Scenario | What they need |
| --- | --- | --- |
| Developer | "Is my `criteria` wording any good?" Iterates on a YAML request file. | Fast loop, readable tables of probabilities, clear validation errors, cost per call |
| Script / CI author | Block a PR if the changelog entry doesn't describe a user-facing change. | `jev noul … --fail-under 0.7`, stable exit codes, no prompts, stdin piping |
| AI agent | Decide which of 12 runbooks matches an alert, from inside an agent loop. | Discoverable commands, JSON in/out, schemas, structured errors, MCP tools |
| Data / ML engineer | Label 50k support tickets with 9 questions each. | `jev batch run`, concurrency control, resume, error records, cost summary |

## 5. Product principles

1. **Humans and agents are equal first-class users.** Every command description, help page and error is
   written so that an agent reading only that text can pick the right command and call it correctly.
2. **stdout is data, stderr is everything else.** Progress, notices, warnings and logs never touch stdout.
3. **Never prompt unless a human is present.** No TTY, `--no-input`, or `CI=true` ⇒ fail with an actionable
   error instead of waiting.
4. **Validate before spending.** Anything checkable offline is checked offline.
5. **Secrets never travel through argv, logs or error messages.**
6. **The contract is the product.** Flags, JSON output shapes and exit codes are versioned API.
7. **Parity with official SDKs** for env vars and retry behaviour, so nothing surprises existing users.
8. **Unofficial and honest about it.** Clear "not affiliated with TypeSafe AI" notice; the binary is named
   after the model (`jev`), not the company.

## 6. Command surface

Noun-verb groups, with the hot path at the top level.

```
jev eval                      Evaluate a full request (state + many questions) in one API call
jev noul   <question>         Ask one yes/no question; returns P(yes)
jev choice <question>         Pick one option from a set you define
jev score  <question>         Rate the state on an ordered rubric (2-10 levels)
jev validate                  Check a request file offline; nothing is sent or billed
jev batch run                 Apply one question set to every row of a JSONL/CSV file
jev models list               List model names/aliases available to the account
jev auth login|status|logout  Store, inspect, or remove the API key for a profile
jev config get|set|unset|list|path
jev profile list|use|create|delete
jev schema request|questions|batch-record|output|error
jev spec                      Dump the entire command tree as JSON (for agents and tooling)
jev mcp serve                 Run as an MCP server over stdio
jev update [--check|--rollback]
jev completion bash|zsh|fish|powershell
jev version
```

Global flags (all commands): `--profile`, `--output/-o json|yaml|table|jsonl`, `--field <path>`,
`--model`, `--base-url`, `--timeout`, `--max-retries`, `--no-input`, `--no-color`, `--quiet/-q`,
`--verbose/-v` (repeatable), `--help/-h`.

Illustrative usage (final flag names are settled in design, the behaviour is the requirement):

```bash
# Full request, many questions, one call
jev eval -f triage.yaml --state-file ticket.txt

# Shell condition: exit 0 if P(yes) >= 0.7, exit 10 if not, other codes on error
if git log -1 --pretty=%B | jev noul "Does this commit message describe a user-facing change?" --fail-under 0.7; then
  echo "needs changelog"
fi

# Choice with an explicit escape option, print just the winner
jev choice "Which team should handle this?" --state-file ticket.txt \
  --option billing="Payments, invoices, refunds" \
  --option technical="Bugs, outages, integrations" \
  --option other --field choice

# Bulk
jev batch run -f questions.yaml --input tickets.jsonl --state-field body --id-field ticket_id \
  --out results.jsonl --concurrency 4 --resume
```

## 7. Functional requirements

### 7.1 Evaluation (`eval`, `noul`, `choice`, `score`)

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-EVAL-1 | `jev eval -f <file>` sends one `POST /v1/systemone` built from a request file containing `questions` and optionally `state` and `model`. `-f -` reads the file from stdin. | M |
| FR-EVAL-2 | Request files are accepted as **JSON or YAML**, detected by extension; `--input-format json\|yaml` overrides (required for stdin when ambiguous). The JSON form is byte-compatible with the API body so docs/Playground examples paste in unchanged. | M |
| FR-EVAL-3 | State sources, in precedence order: `--state <text>`, `--state-file <path>`, piped stdin, `state` in the request file. Exactly one must resolve; ambiguity (e.g. both stdin and `-f -`) is a usage error. | M |
| FR-EVAL-4 | `--state-format text\|json\|auto` (default `auto` by file extension; stdin/flag default `text`). JSON state is sent as an object/array, not a string. | M |
| FR-EVAL-5 | `jev noul <question>` builds a single noul question; optional `--true <desc>` / `--false <desc>` criteria. | M |
| FR-EVAL-6 | `jev choice <question>` takes repeated `--option key[=description]` (description optional ⇒ `null`). Warn on stderr when no escape option (`other`, `none`, `not_stated`…) is present, suppressible with `--no-escape-warning`. | M |
| FR-EVAL-7 | `jev score <question>` takes 2–10 repeated `--level <description>` in order. | M |
| FR-EVAL-8 | Shortcut commands accept `--instructions-file` / `--criteria-file` (JSON/YAML) for structured instructions and criteria (`what`/`not_for`/`examples` objects). | S |
| FR-EVAL-9 | Model resolution: `--model` flag > `model` in the request file > `TYPESAFE_DEFAULT_MODEL` > profile `model` > built-in default `jev-latest`. (A file that names a model is more specific than an ambient default, so it outranks env/profile.) The precedence is stated in `--help`. | M |
| FR-EVAL-10 | Every result surfaces: answers, **resolved model id** (e.g. `jev-1.13.0`), `usage.input_tokens`, **estimated cost in USD**, `x-typesafe-request-id`, and wall-clock latency. | M |
| FR-EVAL-11 | When the requested model is an alias, human output shows `alias → resolved id`; `--warn-unpinned` (config: `warn_unpinned`) emits a stderr reminder to pin a versioned id. | S |
| FR-EVAL-12 | `--dry-run` validates, then prints the exact request body that would be sent (no auth header) and an input-size estimate, and exits without network access. | M |

### 7.2 Gating (exit codes from answers)

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-GATE-1 | `jev noul`: `--fail-under <p>` and `--fail-over <p>` exit **10** when the condition is not met, **0** when met. | M |
| FR-GATE-2 | `jev choice`: `--expect <option>` (repeatable = any of) and `--min-confidence <c>`; unmet ⇒ exit 10. | M |
| FR-GATE-3 | `jev score`: `--fail-under` / `--fail-over` on the score value; `--min-confidence`. | M |
| FR-GATE-4 | `jev eval`: repeatable `--assert '<question-id> <op> <value>'` (ops: `>= <= > < == !=`; value is a number or option key; `<id>.confidence` addressable). All must hold, else exit 10. | S |
| FR-GATE-5 | Gate failure is **never** conflated with an error: the answer is still printed normally, exit code 10 is reserved exclusively for "evaluated successfully, condition false". | M |
| FR-GATE-6 | `--abstain-band <lo>,<hi>` for noul: values inside the band exit **11** ("uncertain") so scripts can route to a human, reflecting the documented guidance that ≈0.5 means "can't tell". | C |

### 7.3 Client-side validation (`validate`, and implicitly before every send)

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-VAL-1 | Validate shape: `type` ∈ {noul, choice, score}; `instructions` present (string/object/array); noul `criteria` only `true`/`false`; choice `criteria` is a non-empty map of `string → string\|object\|array\|null`; score `criteria` is an ordered array. | M |
| FR-VAL-2 | Enforce limits: **≤255 choice options**, **2–10 score levels**, ≥1 question, unique non-empty question ids. | M |
| FR-VAL-3 | Size pre-check using a documented heuristic (originally ~4.5 chars/token + ~270 token overhead; live measurement showed a flat ratio is off by up to 4×, so the implementation estimates per character class, see `docs/context/05-live-test-findings.md`): **warn** near, and **error** clearly beyond, the 64k total / 32k (state + longest question) budgets. The estimate is labelled as an estimate; `--skip-size-check` bypasses. | S |
| FR-VAL-4 | Lint warnings (non-fatal, `--strict` makes them fatal): choice without an escape option; choice with exactly two yes/no-like options (suggest noul); backticked paths using array indices into long arrays (known unreliable); duplicate option descriptions. | S |
| FR-VAL-5 | Errors identify the question id and JSON path, state the rule, and suggest the fix. In JSON mode they follow the error schema (FR-OUT-6). | M |
| FR-VAL-6 | `jev validate -f <file>` runs all of the above offline and exits 0 (valid), 2 (invalid). Works with no API key configured. | M |

### 7.4 Batch (`batch run`)

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-BATCH-1 | Input: **JSONL** or **CSV** (header row), via `--input <path>` or stdin (JSONL only). One row ⇒ one API request using the shared question set from `-f`. | M |
| FR-BATCH-2 | Row → state mapping: whole row object by default; `--state-field <name>` uses one field; `--state-fields a,b,c` sends a trimmed object (state trimming measurably helps accuracy). | M |
| FR-BATCH-3 | Row identity: `--id-field <name>`, else the 1-based input line number. Ids must be unique; duplicates are a validation error before any request is sent. | M |
| FR-BATCH-4 | Output: append-only **JSONL**, one record per row: `{id, status:"ok", model, answers, usage, cost_usd, request_id, latency_ms}` or `{id, status:"error", error:{…}}`. `--out <path>` or stdout. | M |
| FR-BATCH-5 | Bounded concurrency `--concurrency N`, **default 4**; a stderr warning above 8 (documented rate-limit point on shared keys). Global adaptive back-off: a 429/529 on any worker slows the whole pool and honours `retry-after`. | M |
| FR-BATCH-6 | Failure policy: **continue**, record the error, exit **7** (partial failure) at the end. `--fail-fast` stops at first failure; `--max-errors N` stops after N. | M |
| FR-BATCH-7 | `--resume`: read the existing `--out` file, skip ids already recorded `ok`, retry ids recorded `error`, append new records. No separate state database. | M |
| FR-BATCH-8 | Graceful interruption: on SIGINT/SIGTERM stop dispatching, let in-flight requests finish (bounded), flush output, print the summary, exit 130. A second signal exits immediately. Output is always valid JSONL. | M |
| FR-BATCH-9 | Summary on stderr (and as a final JSON object with `--summary-json <path>`): rows total/ok/failed/skipped, input tokens, estimated cost, wall time, throughput, retry count, resolved model id(s). | M |
| FR-BATCH-10 | Progress bar on stderr when it is a TTY; periodic one-line progress otherwise; silent with `--quiet`. | S |
| FR-BATCH-11 | Pre-flight: validate the question set once; `--dry-run` validates input rows and prints projected request count and estimated cost without sending. `--limit N` processes only the first N rows. | S |
| FR-BATCH-12 | `--out-format csv` flattens answers into columns (`<id>.noul`, `<id>.choice`, `<id>.confidence`, `<id>.score`). | C |
| FR-BATCH-13 | Deterministic: output records carry the input id; ordering is completion order by default, `--ordered` preserves input order at some throughput cost. | S |

### 7.8 Output

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-OUT-1 | Default format: **human** (tables, probability bars, colour) when stdout is a TTY; **JSON** when piped or redirected. `--output`/`JEV_OUTPUT`/profile override. | M |
| FR-OUT-2 | Formats: `table`, `json`, `yaml`, `jsonl`. JSON output is a documented envelope: `{model, requested_model, answers, usage, cost_usd, request_id, latency_ms}`; `answers` is passed through from the API unmodified. | M |

### 7.10 MCP server (`jev mcp serve`)

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-MCP-1 | `jev mcp serve` runs an MCP server over **stdio** only. stdout carries protocol frames exclusively; all logs go to stderr. | M |
| FR-MCP-2 | Tools: `evaluate` (state + question map), `noul`, `choice`, `score` (flat single-question schemas), `validate` (offline), `list_models`. | FR-MCP-5 | Uses the normal profile/env resolution (`--profile` on `serve`). The API key is never exposed through any tool, resource, or error. | M |

| FR-MCP-7 | Auto-update never swaps the binary of a running server; staged updates apply on next start. | M |

### 7.11 Updates (`update`, auto-update)

| ID | Requirement | Pri |
| --- | --- | --- |
| FR-UPD-1 | **Auto-update is on by default.** At most once per 24 h, *after* the user's command has finished, a detached check queries GitHub Releases for `shaharia-lab/jev-cli`. It never delays, alters, or fails the user's command. | M |
| FR-UPD-2 | A newer stable version is downloaded to a staging directory and **verified** (SEC-UPD-*). At the start of the **next** invocation the binary is atomically swapped, and a one-line notice (`jev updated 0.3.1 → 0.4.0 — changelog: <url>`) is printed to stderr. On Windows the running-exe rename strategy is used. | M |
| FR-UPD-3 | Opt-out: `JEV_AUTO_UPDATE=false` (also `0`, `no`, `off`) or `update.auto = false` in config. | M |
| FR-UPD-4 | Auto-update is **automatically disabled** when: (a) the install is package-manager managed (Homebrew, cargo, etc. — detected from the executable path/install receipt); (b) `CI=true`; (c) the binary or its directory is not writable (never request elevation); (d) `update.pin_version` is set in config. | M |
| FR-UPD-5 | `jev update` updates now; `--check` only reports (exit 0 current, exit 20 update available); `--rollback` restores the previous binary, which is always retained; `--version <x.y.z>` installs a specific version (downgrade allowed only through this explicit flag). On managed installs it prints the correct package-manager command instead. | M |
| FR-UPD-6 | `jev version` prints version, commit, build date, target triple, install method, auto-update status and the reason if disabled; `-o json` supported. | M |
| FR-UPD-7 | `update.channel = stable \| prerelease` (default `stable`). | S |
| FR-UPD-8 | The first run after install prints a one-time stderr notice that auto-update is enabled and how to disable it. | M |
| FR-UPD-9 | Any failure in check/download/verify/swap is silent in normal mode (logged at `-v`), leaves the current binary untouched, and is retried at the next window. A failed post-swap self-test (`jev version`) triggers automatic rollback. | M |

## 8. Exit codes (stable contract)

| Code | Meaning | Typical reaction |
| --- | --- | --- |
| 0 | Success (and any gate satisfied) | continue |
| 1 | Unexpected/internal error | report a bug |
| 2 | Usage or client-side validation error | fix the command or request file |
| 3 | Authentication/authorisation (no key, 401, 403) | `jev auth login` / fix env |
| 4 | API rejected the request (404, 422) | fix the request |
| 5 | Rate-limited or overloaded after retries (429, 529) | back off, lower concurrency |
| 6 | Network failure or timeout (incl. 408, 5xx after retries) | retry later |
| 7 | Batch finished with partial failures | inspect error records, `--resume` |
| 10 | Evaluated successfully; **gate condition false** | branch in script |
| 11 | Evaluated successfully; answer inside abstain band (FR-GATE-6) | route to human |
| 20 | `jev update --check`: update available | — |
| 130 | Interrupted (SIGINT) | — |

## 9. Reliability requirements

| ID | Requirement | Pri |
| --- | --- | --- |
| REL-1 | Retry policy at **SDK parity**: 2 retries, 0.5 s initial delay, 5 s max, ×2 backoff, 0.25 jitter, 30 s timeout; retry on 408, 429, 5xx (incl. 529) and connection errors; **honour `retry-after`**. All configurable per flag/profile. | M |
| REL-2 | Never retry 400/401/403/404/422. | M |
| REL-3 | Every error path surfaces `x-typesafe-request-id` when the server supplied one. | M |
| REL-4 | Response parsing is tolerant of unknown fields and new answer types (passed through in JSON, shown generically in tables) so an upstream addition never crashes the CLI. | M |
| REL-5 | Output files are written append-only with line-atomic writes; a crash never leaves a half-written JSONL record that breaks `--resume` (a trailing partial line is detected and discarded). | M |
| REL-6 | Config and credential files are written atomically (temp file + rename) with a file lock, so concurrent `jev` processes cannot corrupt them. | M |
| REL-7 | No panics on user input; all failures map to the exit-code table. `panic = "abort"` is not used, so a panic still yields exit 1 with a bug-report hint. | M |

## 10. Security requirements

| ID | Requirement | Pri |
| --- | --- | --- |
| SEC-1 | The API key is never accepted as a CLI argument value, never written to config, logs, error messages, `--dry-run` output, or MCP results. Held in memory in a zeroize-on-drop secret type with a redacting `Debug`. | M |
| SEC-2 | Logging: `-v` logs method, URL, status, timing, request id, retry decisions. **Request/response bodies are never logged** unless `--debug-bodies` is passed explicitly, which prints a warning that `state` may contain sensitive data. `Authorization` is always redacted. | M |
| SEC-3 | `base_url` must be `https://`. Plain `http://` is permitted only for loopback addresses (tests/mocks) or with an explicit `--insecure-allow-http`, which warns on every call. | M |
| SEC-4 | TLS via **rustls** with the platform/webpki roots; certificate verification cannot be disabled. No OpenSSL dependency. | M |
| SEC-5 | Credentials file fallback is created `0600` inside a `0700` directory; the CLI refuses to read a credentials file with broader permissions (Unix) and explains how to fix it. | M |
| SEC-6 | No telemetry, analytics or crash reporting. The only hosts contacted are the configured TypeSafe base URL and, for updates, GitHub Releases for this repository. Documented in README and `SECURITY.md`. | M |
| SEC-7 | `state` and answers are never persisted by the CLI except to output paths the user names. | M |
| SEC-UPD-1 | Release artifacts are **signed in CI**; the public key is compiled into the binary. The updater verifies **signature and SHA-256** before staging, over HTTPS, from the pinned repository only. | M |
| SEC-UPD-2 | Automatic updates **refuse downgrades** and refuse versions older than the embedded minimum; only `jev update --version` can downgrade. | M |
| SEC-UPD-3 | Signing key lives only in GitHub Actions secrets/environment with required reviewers; key rotation is supported by embedding a primary and a next key. Procedure documented in `SECURITY.md`. | M |
| SEC-UPD-4 | The install scripts (`install.sh`, `install.ps1`) verify checksums (and the signature when a verifier is available) before installing to a user-writable directory; they never invoke `sudo`. | M |
| SEC-SUP-1 | Supply chain: `Cargo.lock` committed; `cargo-deny` (advisories, licences, bans, sources) and `cargo-audit` gate CI; Dependabot/Renovate enabled; GitHub Actions pinned by commit SHA; release builds use `--locked`. | M |
| SEC-SUP-2 | `#![forbid(unsafe_code)]` in both crates (exceptions require a documented, reviewed allow). | M |
| SEC-SUP-3 | Each release publishes an SBOM (CycloneDX) and GitHub build-provenance attestations alongside the signatures. | S |
| SEC-MCP-1 | MCP file access is deny-by-default and confined to `--allow-dir` roots (FR-MCP-4); tool inputs are treated as untrusted. | M |
| SEC-DOC-1 | `SECURITY.md` with a private disclosure channel, supported versions, and the update-verification design. | M |

## 12. Architecture and engineering

### 12.1 Workspace layout

```
jev-cli/
├── Cargo.toml                # workspace
├── crates/
│   ├── jev-client/           # library: NO clap, NO terminal, NO filesystem config
│   │   ├── types             #   Request, Question{Noul,Choice,Score}, Answer, Usage, ModelCard
│   │   ├── validate          #   limits, shapes, lints, size estimate
│   │   ├── http              #   reqwest+rustls transport, auth, request-id capture
│   │   ├── retry             #   policy, backoff+jitter, retry-after
│   │   ├── error             #   typed errors mirroring SDK classes
│   │   └── pricing           #   model → $/Mtok
│   └── jev-cli/              # binary `jev`
│       ├── cli               #   clap definitions (single source for help + spec)
│       ├── commands/         #   one module per command group
│       ├── config / auth     #   TOML, profiles, keyring + file fallback
│       ├── output            #   table/json/yaml/jsonl renderers, error renderer
│       ├── batch             #   streaming reader, worker pool, resume, summary
│       ├── mcp               #   stdio server, tool adapters over jev-client
│       └── update            #   check, download, verify, stage, swap, rollback
├── skills/jev-cli/SKILL.md
├── CLAUDE.md   (AGENTS.md → symlink)
└── docs/
```

| ID | Requirement | Pri |
| --- | --- | --- |
| ENG-1 | Cargo **workspace** with `jev-client` (library) and `jev-cli` (binary `jev`). The library has no CLI, terminal, or config-file concerns and is usable as a standalone unofficial Rust client. | M |
| ENG-2 | Dependency direction is one-way: `jev-cli → jev-client`. Commands depend on traits (`Transport`, `CredentialStore`, `Clock`, `UpdateSource`) so each is unit-testable with fakes. | M |
| ENG-3 | Async runtime: `tokio`; HTTP: `reqwest` + `rustls`; CLI: `clap` (derive); serialisation: `serde`/`serde_json`/YAML; errors: `thiserror` in the library, a single top-level error→exit-code mapping in the binary. | M |
| ENG-4 | Request/answer types are `serde` types that also derive JSON Schema (`schemars`), so FR-AGENT-3 schemas, MCP tool schemas and validation share one definition. | M |
| ENG-5 | Quality gates in CI: `cargo fmt --check`, `clippy -D warnings` (pedantic subset), tests on Linux/macOS/Windows, MSRV build, `cargo-deny`, `cargo-audit`, docs build, help/spec snapshot tests. | M |
| ENG-6 | Public items in `jev-client` are documented (`#![warn(missing_docs)]`); the crate follows Rust API guidelines. | S |

## 18. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Compromised release or signing key pushes malware to every auto-updating install | Critical | SEC-UPD-1..4, protected release environment with required reviewers, dual embedded keys for rotation, rollback, provenance attestations, documented incident procedure |
| Upstream API changes (new answer types, renamed fields, moved aliases, limits) | High | Tolerant parsing (REL-4), live smoke suite (TEST-3), price/limits as data, fast release train + auto-update |
| Auto-update surprises users who tuned thresholds or need reproducibility | Medium | Guards (FR-UPD-4), first-run notice (FR-UPD-8), `pin_version`, SemVer discipline, changelog link in the update notice |
| Rate limits on shared keys make batch flaky | Medium | Default concurrency 4, adaptive global back-off, `retry-after`, resume |
| MCP `batch_run` abused to read/write arbitrary files or burn budget | High | Deny-by-default `--allow-dir`, canonicalised path confinement, row and cost caps (FR-MCP-4, FR-MCP-8) |
| Key or customer `state` leaks through logs or error output | High | SEC-1, SEC-2, secret-leak test (TEST-7) |
| Scope: MCP + auto-update + batch is a large v1 | Medium | Milestones are independently shippable as pre-releases; `0.1.0` is cut only after M7 |
| Trademark/naming concern from TypeSafe AI | Low–Medium | Non-affiliation notice, model-name binary, early heads-up (Q5) |

## 19. Glossary

- **State** — the content being judged (string, object, or array).
- **Noul** — yes/no question; answer is P(yes). Has no `confidence` field.
- **Choice** — pick one of ≤255 options you define; returns the winner, all probabilities, and `confidence`.
- **Score** — position on an ordered rubric of 2–10 described levels; returns a probability-weighted value.
- **Confidence** — how peaked the distribution is; not a probability of being correct.
- **Fan-out** — putting every question about the same state into one request (cheaper and faster than N calls).
- **Alias** — a moving model name (`jev-latest`) that resolves to a versioned id (`jev-1.13.0`).
- **Gate** — a CLI flag that turns an answer into an exit code.
- **Managed install** — an install owned by a package manager, for which self-update is disabled.
